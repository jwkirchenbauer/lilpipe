# Matrix RIO final report worker

`run_report.sh` is a prepared one-GPU report worker for the Matrix RIO study.
It does not submit jobs. The report must wait until all eight
main attack cases have complete training, full evaluation, analysis, and
step-profile status; paired defenses and declared endpoints must also pass the
strict comparator checks.

The worker verifies fresh CUDA references before writing reports:

- The pinned base Zephyr scores come from
  `control-study/base-reference/validation.json`. The worker re-verifies its
  full-task WMDP and MMLU result files against the frozen Matrix evaluation
  tasks, expected model path, full sample counts, and recorded signatures.
- The defended MMLU reference comes from the fresh CUDA evaluation of K16
  checkpoint zero in `control-study/cases/hparam-rio-lr1e-6`.
- The parity gate uses `pilots/rio-prefix-new-anchor`. Same-backend simulated
  and genuine updates must match exactly for all 16 losses and parameter
  states 1, 2, 4, 8, and 16. Archived ROCm comparisons are reported as
  diagnostics; they do not require cross-backend bitwise equality.
- `source/precision-audit/results/precision-audit.json` must be complete.
- The separate `backend-control` K4 CUDA defense and 1000-step attack must
  have complete training; the attack's full evaluation includes its step-zero
  defended endpoint. Those scores are compared with the main K4 attack scores
  to write `backend-control-drift.csv`.

The main study keeps its original eight conditions. K256 training is CUDA;
K4, K64, and the fidelity-condition training checkpoints are reused from
ROCm. Every score table generated by this worker is re-collected from full,
verified Matrix CUDA evaluations. The separate K4 control measures long-run
training-backend drift with the same K4 recipe, fixed seeds, sampled batches,
probe set, and saved physical axes. Expected floating-point variation is
allowed between backend training runs. The comparison labels the training
backend explicitly; both score series use CUDA evaluation.

When the declared inputs are complete, invoke from the project root with the
maintainer Matrix launcher and a reviewed one-GPU `pbatch` allocation, passing
the absolute study path. The worker activates the installed CUDA evaluation
prefix and writes the final report and comparison tables under the study root.
